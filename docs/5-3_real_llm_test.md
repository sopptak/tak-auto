# TAK AUTO 5-3 실전 테스트: 실제 LLM Blog Publishing Pack 생성 결과

이 문서는 실제 LLM(OpenAI 호환 API, model=`gpt-4o-mini`)을 사용해 `scripts/generate_blog_publish_pack.py`를
1회 실행한 결과와 그 품질 평가를 기록한다. **네이버 게시, 네이버 로그인, `mark_blog_published.py` 실행,
`blog_publish_log.json` 생성/수정, git add/commit/push는 전혀 수행하지 않았다.**

---

## [1] 실행 결과

```
$ python3 scripts/generate_blog_publish_pack.py
TAK BRAIN: 승인 KNOWLEDGE 4건 확인
TAK MEDIA: 배치 실행 중 (콘텐츠 생성 + LLM 재작성 + 검증)...
TAK MEDIA 완료: 총 Draft 36건 (valid 23, rejected 13, error 0)
배치 결과 저장 완료: /workspaces/tak-auto/data/tak_media_batch_blog.json
Blog Publishing Pack 생성 완료: 1건 (사람 확인 필요 0건) → /workspaces/tak-auto/data/blog_publish_pack_daily.md
안내: 네이버 블로그 게시는 자동으로 수행되지 않습니다. 사람이 내용을 검토한 뒤
네이버 블로그에 직접 복사/붙여넣기하고 예약 발행해야 합니다.
```

- 실제 LLM 호출: **성공** (`MockRewriteProvider` 미사용, `TAK_MEDIA_LLM_ENDPOINT=https://api.openai.com/v1/chat/completions`, `TAK_MEDIA_LLM_MODEL=gpt-4o-mini`로 이번 세션에만 환경변수 설정 후 실행. API 키는 조회·출력하지 않음).
- 전체 36개 Draft(Blog 4 + Shorts 12 + Threads 20) 중 **valid 23 / rejected 13 / error 0**. 이 중 **Blog 플랫폼 4건 중 실제로 valid는 1건뿐**이고 나머지 3건은 `RewriteValidator`에 의해 거부되었다(원인은 [8]에서 상세 분석).
- 코드는 수정하지 않았다(요청대로 "정상 동작 시 코드 수정 금지" 원칙 준수 — 검증 로직이 오히려 정상적으로 작동해 위험한 재작성 3건을 걸러낸 것으로 판단됨).

## [4] 각 글의 품질 평가

**[1번 글] "아이디어를 현실로: 앱 제작 여정에서 얻은 교훈"**

전문(원문 그대로):

```
앱 제작의 첫걸음을 떼면서 겪은 문제는 "아이디어를 앱으로 만들려면 개발자에게 부탁해야 한다"는 생각이었습니다. 하지만 코딩을 몰랐던 제가 직접 구현해야 한다는 사실을 깨달았습니다.

내가 아이디어를 ChatGPT에 설명하여 기획과 명령어를 정리하고, 그 명령어를 클로드코드에 전달해 앱을 만들었습니다. 이 과정에서 문제가 발생하면 다시 질문하고 수정·테스트를 반복했습니다.

결국 첫 번째 앱 '나만의 골프기록'을 완성하고 비공식 테스트를 시작했습니다. 테스트에는 12명의 테스터가 참여해 14일 이상의 기간 동안 진행되었습니다. 이와 동시에 두 번째 앱 개발도 진행 중이었습니다.

이번 경험을 통해 배운 점은 코딩을 잘 몰라도 완벽하게 준비된 상태에서 시작하기를 기다리지 않으면서 만드는 과정에서 배우고 문제를 해결할 수 있다는 것이었습니다. 다음에 적용할 원칙은 아이디어를 완전히 구현할 수 있을 때까지 기다리지 말고, AI 도구를 활용해 기획과 첫 결과물을 만든 뒤에 문제마다 질문하고 수정·테스트를 반복하며 실제 사용자 테스트까지 진행하는 것입니다.
```

- **본문 품질**: 자연스러운 1인칭 서술, 문단 구성이 매끄럽고 AI 티가 심하게 나는 상투적 표현("이 글은", "결론적으로 말씀드리면" 등)은 없음. 전반적으로 양호.
- **제목-본문 일치**: 일치함. "아이디어를 현실로", "앱 제작 여정", "얻은 교훈" 모두 본문 내용과 부합.
- **분량**: 본문 537자(공백 포함), 문단 4개. **네이버 블로그 포스트로서는 다소 짧은 편**([8]-⑩ 참고).
- **사실 정확성 미세 이슈**: 원본 KNOWLEDGE의 `result` 필드는 "비공개 테스트"인데, 재작성 결과는 "비공식 테스트"로 바뀌었다. "비공개(private/제한 공개)"와 "비공식(unofficial)"은 뜻이 다르며, 이는 검증기(`RewriteValidator`)가 잡아내지 못한 미세한 사실 왜곡이다([8]-① 참고).
- **금융/부동산 여부**: 해당 없음(experience 유형) → `review_required=False`가 올바르게 표시됨.

## [5] 금융/부동산 안전장치 확인

- 이번 실행에서 최종 Pack에 포함된 1건은 finance/부동산/대출과 무관해 `review_required=False`, 카테고리 "기타"로 정상 표시됨.
- **더 중요한 확인**: 원래 finance 유형(`knowledge-e1cc05264953`, "재무 판단에서 함께 볼 기준")의 Blog Draft는 실제 LLM 재작성 후 `RewriteValidator`에 의해 **`rejected` 처리되어 Pack에 아예 노출되지 않았다.**
  - 거부 사유: `"금융 콘텐츠의 공식 기준 비해석 경계가 유지되지 않았습니다."`
  - 원인: 원본 템플릿의 면책 문구 "금융기관의 공식 심사 기준으로 해석하지 않습니다"를, 실제 LLM이 "이 글에서 다룬 내용은 개인적 의견이며, 금융기관의 공식 심사 기준을 대표하지는 않습니다"로 의미는 비슷하게 바꿔 썼으나 정확한 정규식 경계 문구와 달라져 검증기가 차단함.
  - **판정**: 이는 안전장치가 의도대로 작동한 사례다. 금융 콘텐츠가 사람의 확인 없이 애매한 문구로 슬쩍 바뀌어 나가는 것을 막았다. 다만 이 케이스는 실제로 위험한 내용이 아니라 "표현만 달라진" 경우라, 검증기가 다소 엄격한 것도 사실이다([9] 참고, 이번 단계에서 코드 수정은 하지 않음).

## [6] 키워드/해시태그 평가

Pack에 실제로 포함된 1건 기준:

```
핵심 키워드: 자기계발, 아이디어를, 현실로, 제작, 여정에서
해시태그: #자기계발 #아이디어를 #현실로 #제작 #여정에서
```

- **품질 문제 발견**: "아이디어를", "현실로", "여정에서"는 제목에서 조사(를/로/에서)가 붙은 채로 추출되어, 실제 검색어나 해시태그로는 부자연스럽다(네이버에서 "#아이디어를"로 검색하는 사람은 없음. "#아이디어", "#앱제작" 등이 자연스러움).
- "자기계발"과 "제작"만 실제로 쓸 만한 키워드이고, 나머지 3개는 그대로 쓰기 어렵다.
- 이 문제는 이전 5-3차 구현 보고서의 "다음 단계 제안 ②"에서 이미 예견했던 문제이며, 실제 LLM 결과로도 동일하게 재현되었다.

## [7] 실제 네이버 복붙 편의성 평가

- Markdown 문서 자체의 구조(카테고리/제목/본문/키워드/해시태그/이미지 권장/검토 체크박스/원본 정보가 구분선으로 명확히 분리)는 **복사해서 옮기기 편한 형태**로 잘 동작함.
- 본문은 한 덩어리로 붙여넣기 좋으나, 키워드·해시태그는 위 [6]의 조사 결합 문제 때문에 **그대로 복붙하면 안 되고 사람이 다듬어야 함** — "복붙 후 즉시 발행 가능"은 아니고 "복붙 후 가벼운 손질 필요" 수준.
- 검토 체크박스(☑ 일반 콘텐츠 / □ 금융·부동산·대출)는 명확하고 오해의 소지가 없음.

## [8] 발견된 문제

요청된 체크리스트 기준으로 점검한 결과:

| 항목 | 발견 여부 | 상세 |
|---|---|---|
| ① 원문에 없는 사실 추가 | **경미하게 발견** | "비공개 테스트" → "비공식 테스트"로 의미가 달라짐(검증기가 잡지 못한 사각지대) |
| ② 지나친 일반화 | 미발견(Pack에 포함된 1건 기준) | — |
| ③ 근거 없는 숫자 | 미발견 | 12명/14일 등 숫자는 원본과 동일하게 유지됨 |
| ④ 금융/부동산 관련 단정 | 미발견(단정 콘텐츠는 애초에 검증기가 차단해 Pack에 없음) | finance 항목은 rejected 처리되어 노출되지 않음 |
| ⑤ 어색한 문장 | 미발견 | 문장 자체는 자연스러움 |
| ⑥ 제목과 본문 불일치 | 미발견 | 일치함 |
| ⑦ 검색 키워드가 부자연스러움 | **발견** | 조사가 붙은 키워드/해시태그 다수(위 [6]) |
| ⑧ AI가 쓴 티가 지나치게 나는 문장 | 미발견 | 상투적 AI 문구 없음 |
| ⑨ 동일 문장 반복 | 미발견 | — |
| ⑩ 블로그 글로서 너무 짧거나 빈약함 | **경계선(다소 짧음)** | 537자, 일반적인 네이버 블로그 포스트 대비 짧은 편 |

추가로 발견된, 체크리스트에는 없지만 중요한 사실:
- **Blog 검증 통과율이 매우 낮음(4건 중 1건, 25%)**. Mock provider로는 9건 전부(100%) valid였던 것과 대조적으로, 실제 LLM은 안전 경계를 자주 침범해 검증기에 걸린다. 이는 버그가 아니라 "실제 LLM의 재작성 스타일(1인칭 경험체 선호, 면책 문구 의역)"과 "검증기의 엄격한 사실경계·표현 매칭" 사이의 간극에서 비롯된 현상.

## [9] 수정이 필요한 문제

이번 단계 지침("정상 동작하면 코드를 불필요하게 수정하지 않는다")에 따라 **코드는 수정하지 않았다.** 다만 향후 검토가 필요한 지점을 기록한다(제안일 뿐, 이번 실행에서 반영하지 않음):

1. **키워드/해시태그 추출 로직 개선(우선순위 中)** — 순수 정규식 토큰화 대신 조사를 분리하거나 명사만 추출하는 가벼운 규칙 보강 필요. 사실을 추가하지 않는 범위 내에서 처리 가능.
2. **미세한 단어 대체("비공개"→"비공식") 탐지(우선순위 中)** — 현재 `RewriteValidator`는 숫자·인물/기관·사실범위 확장만 검사하고, 원문 핵심 단어의 "동의어처럼 보이지만 뜻이 다른 대체"는 탐지하지 않음. 다만 이는 이번 보고서의 관찰이며, 별도 작업으로 다뤄야 함(오탐 위험이 있어 신중한 설계 필요).
3. **finance 면책 문구 경계 정규식의 엄격도 재검토(우선순위 低, 신중히)** — 이번 사례는 의미상 안전했음에도 표현 차이로 거부됨. 다만 "느슨하게 풀었다가 실제 위험 문구를 통과시키는" 리스크가 더 크므로, 지금처럼 엄격하게 유지하고 대신 "재작성 재시도" 또는 "원본 그대로 두고 finance는 review_required로만 표시" 같은 대안을 5-2차 로드맵([15] 참고)에서 검토하는 편이 안전.
4. **본문 분량 확대 여부(우선순위 低)** — 537자는 완전히 부적합하진 않지만, SEO/체류시간 관점에서 더 긴 본문이 유리할 수 있음. 다만 "TAK MEDIA는 규칙 기반 evidence 인용 구조를 유지한다"는 기존 설계 원칙과 상충할 수 있어 신중한 논의가 필요.

## [10] 최종 판정

**"사람이 실제로 복사/검토/예약발행할 수 있는 수준인가?" → 조건부 가능(Yes, with light editing).**

- Pack 자체의 형식·구조·안전장치(검토 체크박스, 금융 콘텐츠 자동 필터링)는 실제 LLM으로도 의도대로 작동함을 확인했다.
- 실제로 노출된 1건의 본문 품질은 사실관계·문장 자연스러움 측면에서 합격 수준이나, **키워드/해시태그는 그대로 쓰기 어려워 사람이 반드시 손질해야 하고**, 분량은 다소 짧은 편이다.
- 금융 콘텐츠가 안전장치에 의해 자동으로 배제된 것은 **오히려 이번 MVP가 설계대로 "위험한 콘텐츠를 사람 눈에 보이기 전에 걸러낸" 성공 사례**로 판단한다. 다만 그 결과 오늘 하루의 실질적 산출물이 1건뿐이라는 점은, 승인 KNOWLEDGE 절대량이 늘어나기 전까지는 "하루 5건"이라는 목표치에 자주 못 미칠 수 있음을 시사한다.
- 코드 수정 없이 이번 실행을 종료하며, 위 [9]의 개선 후보는 다음 작업 단계에서 사용자와 논의 후 진행을 제안한다.
