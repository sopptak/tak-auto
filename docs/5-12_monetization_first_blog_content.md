# TAK AUTO 운영 전환 — 검색 유입형 첫 네이버 블로그 콘텐츠 (2026-09-16)

이 문서부터 TAK AUTO의 운영 기준이 "개발 완성도"에서 "실제 수익화(검색
유입 → 콘텐츠 생산 → 트래픽 → 수익)"로 바뀐다. 이번 작업은 그 첫 번째
목표 — "검색 유입을 노린 네이버 블로그 글 1개를 실제 운영 가능한 상태로
만드는 것" — 를 위해 저장소를 분석하고, 기존 기능을 그대로 재사용해 실제
콘텐츠를 만든 기록이다. **새 기능/코드는 추가하지 않았다.**

## 1. 저장소 분석 요약

- SCOUT → INTERVIEW → KNOWLEDGE → MEDIA(Blog/Shorts/Threads) → Dashboard
  검수 구조는 이미 전부 구현되어 있다(457개 테스트, 전부 통과 확인).
- **Blog 파이프라인도 이미 존재한다**: `scripts/generate_blog_publish_pack.py`
  가 승인 KNOWLEDGE → TAK MEDIA(LLM 재작성) → `data/blog_publish_pack_daily.md`
  (사람이 복사/붙여넣기용 Markdown)를 만든다. 네이버 자동 게시는 정책상
  구현하지 않는다(요청한 것과 동일한 "AI 생성 → 사람 검수 → 사람이 직접
  게시" 구조가 이미 그대로 있음).
- 승인된 KNOWLEDGE 8건 중 **금융/대출 실전 경험 기반은 1건뿐**:
  `knowledge-e1cc05264953`("은행에서 대출받을 때 재무제표에서 가장 먼저
  보는 것은?") — 티몽 본인이 이미 실제로 쓴 글(`blog.naver.com/tmong2/224407146649`)
  에서 추출된 KNOWLEDGE다. SCOUT가 새로 물어온 "금융" 카테고리 항목들은
  전부 영국발 AI/경제 뉴스 재탕이라 대부분 rejected 상태이고, 티몽의 실제
  대출·재무제표 전문성과는 무관하다 — 첫 콘텐츠 소재로 쓸 수 없다.
- **중요 발견**: `data/tak_brain_raw.json`에 이 KNOWLEDGE의 원문 전체
  (티몽이 실제로 쓴 풀텍스트, 이미 네이버에 발행된 글)가 그대로 남아있다.
  반면 TAK MEDIA의 규칙 기반 생성기(`content_engine/generator.py`)와
  안전 검증기(`content_engine/rewrite.py`의 `RewriteValidator`)는 **KNOWLEDGE
  의 압축된 1~2문장 필드만 인용**하고, **원문에 없는 새 숫자·사실은
  추가하지 못하도록 의도적으로 막는다**(허위/과장 방지용 안전장치). 그
  결과 자동 생성 Blog Draft는 4문장짜리로 매우 얇고, 제목도
  `"대출 판단을 위한 재무 지표 확인하기"`처럼 검색 의도가 약하다 — 아래
  3번 참고. 이건 버그가 아니라 "새 사실을 지어내지 않는다"는 설계가 만든
  당연한 한계다.

## 3. 무엇이 실제로 작동하는가

- 파이프라인 자체는 **정상 작동한다**: 승인 KNOWLEDGE → 실제 LLM 호출 →
  안전 검증(원문에 없는 숫자·사실·금융 면책 문구 훼손 여부 자동 차단) →
  Markdown 결과물까지 한 번에 끝까지 돈다. 오류 없음.
- 다만 결과물 품질이 "그대로 게시 가능한 수준"은 아니다:
  - 본문 4문장, 제목 `"대출 판단을 위한 재무 지표 확인하기"`(검색 의도가
    막연함)
  - 키워드 제안이 제목에서 정규식으로 토큰만 뽑아 `"판단을", "위한"`
    같은 조사 섞인 값까지 나옴(문서 자체에 "참고용 제안, 검색 순위·조회수
    보장 안 함"이라고 명시되어 있어 설계상 알려진 한계)
  - → **이 결과물 단독으로는 "검색 유입형 첫 글"의 기준(①검색 의도가
    명확한 제목 ②독창적 분량/구성)을 못 채운다.**

## 4. 그래서 실제로 만든 것 — `data/blog_draft_01_loan_key_metrics.md`

파이프라인의 한계를 메우기 위해, **같은 KNOWLEDGE의 RAW 원문(티몽 본인이
실제로 쓴 글)에 실제로 있는 사실·숫자만 그대로 가져와**, 지시사항의 예시
제목 중 하나인 **"대출 심사에서 매출보다 중요한 숫자는 무엇인가?"**로 새로
구성한 사람 검수용 초안을 만들어 `data/blog_draft_01_loan_key_metrics.md`
에 저장했다.

- 이 제목을 고른 이유: 이미 발행된 기존 글(`"...재무제표에서 가장 먼저
  보는 것은?"`)과 제목이 겹치면 같은 저자의 콘텐츠끼리 검색 순위를
  잠식(카니발라이제이션)할 위험이 있다. RAW 원문의 가장 차별화된 핵심
  메시지("매출보다 이익이 중요하다")를 그대로 담고 있으면서도, "매출은
  있는데 왜 대출이 안 나올까"라는 실제 검색 행동과 더 직접 맞아떨어지는
  질문형 제목을 새로 골랐다.
- 본문은 RAW 원문의 문장을 그대로 복사하지 않고 새로 썼지만, **숫자·용어·
  절차(10억/30%, 영업이익·당기순이익·이자보상능력, 금융거래확인서·
  부채증명원 등)는 전부 원문에 실제로 있는 것만** 썼다 — 파일 맨 아래
  "사실 출처 대조" 표에 문장 단위로 근거를 남겼다.
- 딱 한 군데("23년째 금융 현장")만 이 RAW 글 자체가 아니라 사용자의 이번
  작업 지시문 + 같은 저자의 다른 승인 글들의 "23년차" 표현에서 가져왔다.
  이 부분은 표에 명시적으로 표시해 두었고, **게시 전 티몽 본인이 숫자가
  맞는지 반드시 확인해야 한다.**
- 금융 면책 문구("공식 심사 기준으로 해석하지 않습니다")를 원문과 동일한
  취지로 유지했다.

## 6. 아직 사람(티몽)이 해야 하는 것

1. `data/blog_draft_01_loan_key_metrics.md`를 열어 내용을 읽고,
   - "23년째 금융 현장" 경력 서술이 정확한지 확인/수정
   - 문체·표현이 본인 톤과 맞는지 다듬기
   - 카테고리·해시태그는 참고용 제안일 뿐이므로 그대로 쓸지 결정
2. 확인이 끝나면 **직접** 네이버 블로그에 복사/붙여넣기하고 예약 발행.
   (TAK AUTO는 정책상 네이버 자동 로그인/자동 게시를 구현하지 않는다 —
   이번에도 그렇게 하지 않았다.)
3. 게시 후 `scripts/mark_blog_published.py`로 게시 완료를 기록해야, 다음
   Pack 생성 때 같은 KNOWLEDGE가 후보에서 자동으로 빠진다(기존 기능,
   이번에 실행하지 않음 — 실제 게시 전이라 아직 기록할 대상이 없음).
4. 이 글이 실제로 검색 유입/조회수를 만드는지는 네이버 블로그 통계에서
   사람이 직접 확인해야 한다(자동 추적 기능은 8번 참고).

## 7. 다음 수익화 단계 (제안, 아직 실행하지 않음)

1. **1건 실제 게시 → 성과 확인**: 위 초안을 게시한 뒤 최소 1~2주 조회수·
   검색 유입 추이를 지켜본다. 이게 이 전략 전환의 첫 검증 포인트다.
2. **생산량 확대**: 승인 대기(pending) 중인 KNOWLEDGE 6건은 전부
   직장생활/자기계발/독서 카테고리다 — 금융만큼 조회수가 좋았다면
   이쪽도 같은 방식(RAW 원문 기반 재구성)으로 2~3건 더 만들 수 있다.
   단, 새로 금융/대출 소재를 늘리려면 SCOUT가 지금처럼 해외 뉴스가
   아니라 **한국 대출/재무 관련 국내 소재**를 물어오도록 소스 설정을
   바꿔야 하는데, 이건 "새 기능 추가"가 아니라 기존 SCOUT 소스 설정 값
   조정 범위인지 먼저 확인이 필요하다(다음 턴에서 판단).
3. **Threads/Shorts 재활용**: 이 KNOWLEDGE는 이미 Threads로 1회 발행된
   이력이 있다(`content-ff8909844fa80b99`, `threads_publish_log.json`).
   블로그 글이 실제 게시되면, 그 블로그 글을 홍보하는 형태의 Threads
   글(예: "재무제표에서 매출보다 먼저 보는 숫자, 블로그에 정리했습니다")
   로 트래픽을 유도하는 것이 이 KNOWLEDGE를 다시 쓰는 것보다 낫다 — 이건
   현재 자동 로직에는 없는 조합이라 사람이 수동으로 판단해 Threads
   Dashboard에서 직접 작성하는 게 가장 빠르다.
4. **AdPost/제휴 조건 충족**: 블로그 콘텐츠가 몇 건 쌓이고 조회수 데이터가
   생기면, "인기 주제/게시글별 성과 기록" 구조가 필요해진다. 지금은 이걸
   추적하는 기능이 없다 — 이건 실제로 게시된 글이 1~2건이라도 생긴
   **이후에** (검색 유입 증가에 직접 도움이 되는 시점에) 최소 기능으로
   추가할지 판단하는 게 맞다. 콘텐츠가 하나도 없는 지금 만들면 사용할
   데이터가 없어 3대 기준(검색유입/생산량/수익화) 중 어느 것도 당장
   충족하지 못한다.
